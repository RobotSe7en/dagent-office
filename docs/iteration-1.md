## 目标与演示闭环

完成以下可操作链路：

```text
打开 HTML 文档包或 DOCX → 预览与富文本编辑 → 派生分页
    → 文字划选或矩形框选 → 添加多条批注 → 请求与提案往返
    → 查看差异 → 整批应用 → 撤销或重做 → 导出 DOCX/PDF → 重开核对
    → 独立闭环通过后接入达智现有智能体验证
```

SDK 提供文档预览和批注界面。宿主提供既有智能体入口、模型执行和任务状态；SDK 不新增模型代理、独立 AI 弹窗或智能体运行时。

按三个阶段推进：A 在已有包基础上先完成三格式模型设计、DOCX 读取映射和只读预览验收，B 再完成事务、交互、人工输入、分页及 Word 导出闭环，C 最后接入达智。独立 Playground 使用固定提案验证文档侧完整链路；达智挂载相同组件，通过现有消息、附件和提案产物验证真实智能体交互。两个宿主都通过 SDK 公开入口消费。

### HTML、元数据和样式基线

首批正文结构覆盖 `article`、`section`、`div`、`h1` 至 `h6`、`p`、`span`、`strong`、`em`、`u`、`s`、`sub`、`sup`、`br`、`ul`、`ol`、`li`、`table`、`thead`、`tbody`、`tfoot`、`tr`、`th`、`td`、`img`、`ins` 和 `del`。文档外壳保留必要的 doctype、语言、字符集、标题及包内样式引用。

正文根、段落、标题、列表及条目、可定位行内节点、表格、行、单元格和图片具有稳定 ID；纯结构表格分组可不作为独立操作目标。已有包检查 ID 唯一性和必要节点身份，新片段由核心分配 ID。后续适配器在生成初始文档包时补齐身份。

保留支持的 `class`、行内 `style`、`data-node-id`、`data-office-kind`、语义扩展属性、表格合并以及图片的包内路径、尺寸和替代文字。扩展属性不授予访问权限；未支持的节点或语义明确报错，不悄悄剥离后保存。

以下样式基线是起始实现范围，按[保真目标](document-format.md#保真目标)持续扩展。优先保留原文档样式，局部编辑不重置未修改部分的格式；当前尚未支持的普通样式与安全禁止项分别记录。样式保留、预览、编辑和导出能力分别验证，不以编辑命令的覆盖范围限制源样式的保留。

样式基线包含：

- 选择器：元素、类、节点属性、后代和分组选择器，以及报告使用的 `:root`。
- 文字：颜色、字体族、字号、字重、字形、装饰、对齐和行高。
- 盒模型：宽高、内外边距、边框、背景色和表格边框合并。
- CSS 变量声明及 `var()` 引用；核心保留其语义，浏览器计算显示值。

`setStyle` 写回行内声明，原样式表保持顺序并继续参与级联。核心不实现第二套完整浏览器排版。样式解析使用明确的支持表及值检查，拒绝脚本、处理器、可执行嵌入和未授权资源地址。

元数据覆盖示例中的标题、语言、页面设置、节到根节点引用，并扩展 Word 编号、样式关联及页眉页脚引用。图片先覆盖 PNG、JPEG、WebP；SVG 等扩展在对应格式能力阶段实现。资源校验路径、MIME、摘要和引用，替换生成新资源描述。派生分页容器、选区高亮和宿主主题不进入文档源。

## 工程与公共接口

### 工程基线

采用 pnpm workspace、TypeScript strict、ESM 及类型声明。建立 `core`、`editor`、`office`、`node` 四个库模块和 Vite Playground。具体发布包名与第一方许可证在发布前确定。

核心源码使用不包含 DOM 和 Node 专属能力的类型环境。编辑器主实现使用 DOM 组件；React 作为可选包装入口，复用相同界面并适配生命周期。Playground 验证 React 消费，另用最小普通 JS 宿主验证挂载入口。

开发检查包含类型、构建、核心单元测试、浏览器交互、包依赖方向及打包消费。Vitest 承担核心与协议测试，Playwright 承担界面及固定环境截图。禁止宿主或包跨入口导入内部源码。

`office` 首轮交付文档包 ZIP、DOCX 导入与原生导出；`node` 从文档包检查 CLI 扩展到受管理的 Chromium、固定字体、布局测量、截图和 PDF。转换请求具有精确版本、任务 ID、授权输入、选项和有界结果，不持有模型凭据。

Playground 的 Vite 开发宿主通过仅限本机开发的转换中间件调用 Node 子进程，使用同一字节协议完成 PDF 和服务端渲染；SDK 本身不开放公网监听。达智阶段由 Python 适配和管理相同的进程协议。正式部署、草稿及工作区提交在第四轮完善。

### 契约与校验来源

采用 Zod 4 定义可转换的结构契约，推导 TypeScript 类型并导出 JSON Schema。协议结构不混入无法导出的转换逻辑；节点引用、锚点、修订、样式及资源关系在业务校验中处理。

第三方类型不成为公共文档模型。HTML 使用 parse5，CSS 使用 CSS Tree，具体版本经验证后锁定。记录所用依赖和字体的版本及许可。

## 事务、候选与历史

R1-06 已按以下顺序实现，API、预算及边界见[核心事务与历史](document-session.md)。R1-07 已补齐精确锚点与批注映射。操作和修订语义以[交互协议](editing-protocol.md)为准：

1. 实现只读快照及独立候选，保证准备阶段无当前状态副作用。
2. 先完成 `replaceText`、`setStyle`，运行报告提案；再补区块、图片及批注操作。
3. 按顺序在候选中检查范围和原文，所有目标身份来自基准快照，新节点由核心分配。
4. 校验候选完整结构和引用，计算内容差异、受影响节点及锚点映射。
5. 提交时复核会话和修订，净变化一次提交、一次撤销；失败或无变化保持历史不变。
6. 撤销重做使用新的单调修订，撤销后新编辑清除重做分支。

首轮用前后状态快照形成历史，不提前实现持久化增量日志或语义合并。图片字节不可变并共享引用。输入、节点、操作、资源、上下文和历史均设置明确、可配置的预算并测试超限行为；实际支持规模根据样例测量记录，不把理论限额当性能承诺。

核心只处理语义差异，候选布局与视觉差异由预览层派生。候选绑定会话及基准修订，不允许跨会话或重复提交。

## Word 导入、人工编辑与导出

### DOCX 导入

先解析 ZIP/XML、关系和资源，映射文字片段、段落样式继承、编号、表格及合并、图片、页设置、节和页眉页脚。生成稳定节点 ID、规范 HTML、CSS、元数据及能力记录，初始修订为 0。

保留原文件用于来源与视觉对照，后续编辑和导出仅依赖当前文档源。无法表达的结构明确报告；不把整页图片作为可编辑 Word。已有 HTML 也经统一规范化进入相同模型。

### 富文本输入

Tiptap 负责输入法、光标、选择和支持的文本命令。自定义节点保留节点 ID 与支持属性；其事务转换为核心操作并在校验后同步视图。输入法组合过程只允许暂态输入，不能成为另一份保存源。

实现正文和表格内输入、跨段落选择与替换、基础字符格式、段落格式及受支持内容粘贴。粘贴使用同一 HTML/CSS 校验。核心拒绝操作时视图回到有效状态，不能只修改编辑器 JSON。

核心拥有唯一持久化撤销历史，Tiptap 不独立维护可推进文档的第二套历史。人工输入、脚本和宿主提案都通过同一事务及锚点映射。

### 分页、DOCX 与 PDF

先完成连续流输入，再派生页面视图。页面宽高、页边距、节、页眉页脚及明确分页来自文档源；自动分页不切断正文。验证中文字体、跨页表格、长段落、选区和输入法与分页配合。

DOCX 从修改后的语义 HTML、元数据和有效样式编译原生文字、段落、列表、表格及图片，保留支持的节和页眉页脚。导出文件在参考 Office/WPS 中打开无需修复，重新导入后核对修改及未修改内容。

PDF 使用 Node/Chromium 的固定字体与布局环境输出，检查分页、溢出和遮挡。导入对照原 DOCX，导出对照修改后的 HTML，不以导出视觉修正覆盖用户内容。动态字段及复杂对象按能力矩阵报告可编辑范围和限制。

## 预览、文字划选与框选

预览在隔离的文档容器中显示规范 HTML 和 CSS。资源路径转换为当前会话授权的运行时 URL，序列化仍保留包内路径。宿主主题与文档样式隔离，脚本不执行。

文字划选转换为节点内 UTF-16 范围；跨节点选择按文档顺序形成同一条批注的多个范围。换行与内嵌对象遵守统一表示。

矩形框选在逻辑渲染面上保存 pt 坐标，计算时去除滚动和缩放影响。命中多个节点时保留节点集合；没有命中内容时仍可形成区域批注并提供所属容器和邻接结构。

连续视图使用正文渲染面，分页视图使用实际派生页面。区域锚点保留页面及布局环境标记，布局变化后无法稳定映射时标记为 `needs_reanchor`。文字和节点锚点优先按核心映射更新；保留原摘录与区域供人工定位。

工作台提供批注填写和统一提交，不增加模型选择、AI 润色弹窗或独立聊天。操作演示按钮只在 Playground 展示，标准组件提供通用文档操作和提案界面。

## 请求、提案与应用

### 请求生成

选定的开放批注和相关完整子树冻结为 `DocumentInteractionRequest`，携带文档、修订、请求 ID、HTML、样式、必要元数据、资源描述和支持操作。原示例的完整正文较小，可作为一个根区块提供。

相关上下文使用完整子树，重叠区块合并。不能把裁剪父节点作为可整体替换的完整节点。超限不静默截断请求，由宿主决定缩小范围或分段规划。

生成请求、临时选择和统一提交本身不推进修订。宿主回调接收数据后，在现有任务入口处理整体要求、模型、提示词和运行状态。

### 提案接收

宿主回传原请求及结构化 `EditProposal`。先检查协议、请求 ID、文档、基准修订、批注子集、支持操作及上下文目标，再进入同一核心事务。

新 HTML、CSS 及资源引用按文档规则校验。旧修订、错配请求和不支持操作返回明确错误，保留原文档和原批注。用户补充要求通过宿主重新产生基于当前修订的请求与完整提案，不在旧候选上隐式叠加。

### 用户应用

候选预览包含内容和样式差异、受影响节点及批注状态变化。第一版提供逐处查看、整批应用和整批撤销。

有效内容提交与已处理批注的状态变化属于同一笔事务。未处理批注继续开放，无法映射的目标保持 `needs_reanchor`。拒绝、失败、空操作或无净内容变化不会自动解决批注。

## 达智最小接入

先通过 R1-14 独立 Word 闭环，再进入达智验证；正式保存见第四轮和[达智集成](dagent-integration.md)。

1. 在现有预览区域增加文档协作入口和薄包装组件，使用 SDK 公开入口。
2. 加载合成报告、HTML 文档包或已授权 DOCX；复用已完成的导入，不从既有 PDF 预览反推编辑结构。
3. 提交批注时保留原请求，将结构化请求文件作为现有智能体消息的附件。
4. 宿主沿用当前主体的智能体、模型配置、凭据、Run、Review 和取消机制，要求结果为提案 JSON 产物。
5. 用户选定相应结果后，宿主按现有授权产物读取链路取得提案，并回传组件。
6. 文档组件校验和预览，用户接受后只更新当前会话；验证文档包、DOCX 和 PDF 导出及重开，Python 按需适配同一 Node 转换协议。

最小接入不建设专用 LLM 接口或模型代理，不新增持久化表。Agent 生成提案文件遵守现有 Run 产物和工作区规则；提案产物成功、文档会话提交和正式文件保存分别反馈。原历史产物和来源文件保持不变。

首轮不要求自动识别并应用所有智能体结果。回传入口按请求、文档、修订和宿主所有权关联，关闭或切换文档后不把迟到结果注入另一会话。权限、运行失败或取消后，宿主保留已有请求和批注供用户查看。

## 技术验证与样例

| 验证项 | 最小验证 | 结果记录 |
| --- | --- | --- |
| HTML/CSS | 报告、节点身份、继承、变量、行内修改及往返 | 解析器、支持结构、差异和限制 |
| Tiptap | 自定义节点 ID、样式、中文输入法、跨段落及表格输入、核心事务映射 | 首轮正式输入能力、统一历史和支持限制 |
| DOCX | 段落、继承、编号、表格图片、节、页眉页脚及原生导出重开 | 首轮全链路可编辑性、字体、分页及未覆盖项 |
| Chromium/PDF | 固定字体、派生分页、布局测量、截图和 PDF 输出 | 字体环境、溢出遮挡、渲染版本及子进程回收 |
| PPTX | 原生文字、图片、形状及表格输出 | 对象类型、几何、重开及视觉差异 |
| XLSX | 值、类型、公式、数字格式和计算器桥接 | 缓存与实际计算的区分、依赖更新 |
| ZIP | 原始路径、重复项、摘要、完整资源及有界展开 | 适配器版本和限额行为 |
| 包消费 | 普通 JS、React、Node 使用打包产物 | 公开入口、依赖及类型问题 |

Office 样例至少 18 份：Word 8 份，PPT 和 Excel 各 5 份。Word 样例进入读取及后续正式闭环：中文与行内样式/列表、表格与合并、图片、样式继承与节/页眉页脚、长文档及明确分页、链接与制表位、简单/复杂/嵌套字段、原生批注与文字修订；PPT 和 Excel 样例用于几何、对象、类型和公式的提前验证。核心另准备无效版本、HTML、CSS、引用、操作、冲突和锚点夹具。

真实用户文档保留在私有目录，不能提交或发送给未授权的服务。依赖与字体记录实际版本和许可，候选依赖验证失败时先记录阻塞及最小原因，不用整页图像绕过可编辑性验收。

## 首轮演示脚本

使用[报告包](../examples/report/)、[请求示例](../examples/report.request.json)和[提案示例](../examples/report.proposal.json)：

1. 在 Playground 首先导入 DOCX 样例，再打开其保存的文档包与 HTML 报告，显示标题、正文、样式、表格和分页。
2. 实际输入中文，编辑跨段落及表格内容、调整基础格式，确认核心撤销重做正确。
3. 划选正文，批注“改为第四季度完成，补充系统上线和用户培训”。
4. 框选标题，批注“标题改为深蓝色”；另验收跨节点、空白及分页区域。
5. 使用对应当前修订的请求和固定提案，查看正文与样式差异并整批应用。
6. 撤销、重做，确认修订号单调增长且批注随历史正确恢复。
7. 下载文档包、DOCX 和 PDF；重开文档包，DOCX 在参考应用打开并重新导入，PDF 核对分页。
8. 独立闭环通过后，在达智现有预览区域挂载相同组件并加载授权文档。
9. 统一提交两条批注，通过达智现有智能体入口填写整体要求并发起任务。
10. 取得真实提案 JSON，回传原请求和结果，预览、应用并验证 Word 导出。
11. 请求执行期间用同一核心操作修改正文，确认旧提案被拒绝且可查看。

示例包初始已含两条批注，因此初始修订为 0。实际交互中新增批注会产生事务，提交请求须使用新增批注后的当前修订，不硬编码示例的 0。

## 完成定义

首轮完成必须同时具备：

- 声明范围内的 HTML/DOCX 往返、输入、分页、事务、历史、锚点、请求和提案测试通过。
- 可运行的默认工作台和独立 Playground，普通 JS、React 与 Node 消费打包产物。
- 独立 Playground 的 Word 文件闭环先通过，再由达智现有智能体完成多批注真实修改和导出验证。
- 原生 DOCX 在参考应用重开无需修复，重新导入保留修改；PDF 在固定字体环境满足分页基线。
- 首轮技术验证、样例、支持矩阵、资源及输入预算、接入和生命周期说明齐全。
- README 准确说明已实现范围；计划能力不描述为已发布行为。

除明确标注完成的任务外，本细则定义待实现与验收能力。提交、推送、包上传和对外发布按用户明确指令进行。
